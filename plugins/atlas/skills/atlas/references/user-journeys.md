# User journeys and accessible interaction

Use when an interactive change needs end-to-end, usability or accessibility evidence, including localization and command-line or script-facing behavior. Identify the users, platform, critical journey, accepted interaction and available test environment. Use existing approved browser/device/test capabilities; this runbook does not require a browser package or hosted artifact service.

For a new/revised screen or concerns about hierarchy, clarity or product fit, read [Product interface review](product-design-review.md). When the claim depends on actual user understanding or needs, use [User research](user-research.md); a successful scripted journey is not a participant study.

Follow the user's goal through the real interaction and observable result. Include relevant loading, empty, success, error and retry states, repeated actions, navigation and persistence. Assert meaningful results rather than only that a button was clicked. Isolate test data and avoid real purchases, messages or account changes without applicable authority. Wait for the relevant condition rather than arbitrary delays; record a failure before attempting recovery.

Before reproducing a defect, identify the observable state that separates correct from broken behavior; setup or loading may resemble the reported symptom without being the defect. Arrange legitimate preconditions, then exercise the real boundary under test. Injecting the final state does not prove the action produced it. Check materially different affected entry paths and name the path actually exercised. For persisted changes, use a separate read or reopen where available; a success notification alone is insufficient.

When the requested environment is unavailable, use a safe equivalent only for the conditions it preserves and label the result as translated evidence. If platform, permissions, timing or device behavior matters to the defect, keep that exact claim unverified. Match repetition to statefulness, intermittence and measurement needs; no fixed number of runs establishes every claim. For recurring setup or reset difficulty, use [Establish project verification](project-verification.md).

For browser automation, prefer stable semantic locators and assertions tied to the user's observable result. Approved API or fixture setup may arrange preconditions, but must not replace the UI action being tested. Isolate accounts/data across runs and workers when the backend is shared.

Inspect semantic name/role/value, keyboard reachability, logical focus order, focus movement and restoration, status/error announcements, non-color cues and usable zoom/text scaling/reflow. Prefer native controls when they supply the right interaction. For a modal, check opening focus, contained navigation, dismissal and return to the invoker. A screenshot cannot prove keyboard or assistive-technology behavior; automated accessibility checks alone do not establish conformance. Verify any claimed standard/version and required criteria from authoritative project or standards sources. Record the browser, platform and assistive-technology combinations actually checked; one combination or automated scan does not establish every supported environment.

Match responsive/device checks to the actual layout and supported platforms. Check that visual polish preserves content hierarchy, readability and functional states. Aesthetic scores cannot override broken tasks or required accessibility. Use [client state](client-state-checks.md) when lifecycle or stale responses explain the failure.

When the goal is visual preservation, capture the accepted baseline and relevant states before changing the interface. Compare with consistent viewport, fonts, data and rendering conditions using available image-comparison tools and inspection. Investigate unexpected differences; never replace the baseline simply to hide a regression. Use agreed tolerances and intentional changes rather than universal pixel identity. A visual match does not establish interaction or accessibility, and an accidental baseline defect does not become a new requirement.

For localization, identify supported locales, scripts and time-zone semantics. Exercise representative plural forms, text expansion, right-to-left layout and mixed-direction content, locale-aware input/output and grapheme-sensitive edits where relevant. Distinguish a date-only value from an instant shown in a time zone. Pseudolocalization can reveal layout or untranslated-string defects, but does not establish translation quality or cultural fit. Use [Types and invariants](types-and-invariants.md) for representation and conversion boundaries; avoid blanket normalization or fixed expansion rules.

For CLI and script users, follow invocation through observable output and exit status in both interactive and noninteractive use. Inspect stdout/stderr contracts, machine-readable output, configuration precedence, help and actionable errors. Prompts, progress text or color can corrupt pipelines or hang unattended callers. Exercise the relevant supported invocation and failure path; preserve established flags and output contracts instead of redesigning a command around aesthetic preferences.

For public pages whose goal includes search discovery, inspect intended indexing, canonical/redirect behavior, crawl directives, meaningful links and structured-data consistency. Internal/private pages may correctly be non-indexable. Verify current search-engine rules before promising compliance or ranking outcomes; do not manufacture SEO requirements for an internal app.

Keep traces/screenshots/logs only where they help diagnose or prove the claim, inside the approved environment. Separate live interaction, screenshot inspection, static code analysis and automated tests in the report. A flaky test is unresolved evidence; quarantine or reduced coverage must stay visible and follow project policy. Stop when the important journey claims are proven or a concrete missing capability prevents verification.
