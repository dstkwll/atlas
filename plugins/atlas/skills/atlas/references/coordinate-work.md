# Coordinate work

Use when contributions must fit together, shared resources constrain progress, results arrive at different times, or integration uncertainty makes a simple task list inadequate. This can involve one agent over time, bounded workers, people or an operator event. A clear direct task or one ordinary worker needs no separate coordination exercise.

Choose only the reasoning and pattern that resolve the present uncertainty. The lead retains the outcome; this guide creates no standing staff, runtime, queue, inbox or universal sequence.

## Shape work around the integrated outcome

Recover the accepted outcome, current authority and existing plan. Identify the combined result and the evidence that can assess it now. Distinguish planning, implementation and acceptance: permission to design a run is not permission to launch it, and available software checks may leave physical claims pending.

Identify what each contribution actually needs from another: a decision, contract, artifact, access or evidence. Separate prerequisites for doing useful work from evidence needed to accept the final result. Preserve the exact dependency and its owner or next investigation; one unavailable resource or unsettled policy should not stop unaffected authorized work. For each proposed blocker, explain which output actually depends on the missing detail. If a shared contract has a settled independent portion, use that portion for ready work rather than freezing the whole contract until every policy or integration question is resolved.

Choose the lightest arrangement that can deliver and assess the result. Extra participants should supply useful capacity, expertise or independence. Keep an integration owner and make shared assumptions explicit enough for contributions to fit. The same lead can hold several responsibilities; naming a responsibility does not require a separate actor.

## Select a useful pattern

- **Serial uncertain work:** investigate or complete the dependency that changes later work, then refine the next unit. Use a representative pilot only when it tests the approach, brief or integration arrangement. A pilot does not prove every subsequent slice or extend the budget.
- **Independent contributions with integration:** establish the shared contract sufficiently, separate write surfaces, collect bounded returns and check the combined candidate. If the purpose is comparison of competing proposals, use [Arena](arena.md) and its confirmation boundary instead of treating exploration as implementation fan-out.
- **Work around a scarce verification event:** prepare feasible changes and checks independently, group compatible evidence needs for the operator, and reconcile actual returns by claim and configuration. [Project verification](project-verification.md#when-evidence-depends-on-equipment-or-an-event) owns event preparation and evidence handling. Batching needs does not authorize scheduling, operation or acceptance decisions.

These patterns can be combined where justified; they are not stages every task must complete. Use [tickets](to-tickets.md) for durable executable slices and [handoff](handoff.md) for a continuing session, preserving their readiness requirements. Do not turn every prerequisite into a ticket.

## Assign and proceed within bounds

When assignments are needed, apply [Deliver and repair](deliver-and-repair.md#use-workers-selectively) for source context, permissions, write surfaces, actual isolation, expected evidence, stop/return conditions and recovery. Keep the common contract, integration responsibility and practical cumulative resource bounds visible in the existing plan or briefs. Avoid concurrent mutation of shared files or equipment. Do not assume a host supplies execution, isolation or communication merely because a plan names workers.

Launch only authorized, ready work. Agreement with a planning-only breakdown does not authorize implementation or dispatch. If the current assignment already covers execution, ordinary bounded assignments need no renewed approval. Preserve waiting work with the specific decision, access or result needed and the next useful action; operator duties do not grant product-policy or acceptance authority.

## Integrate actual returns

Inspect the artifacts and supporting evidence, not just completion reports. Compare contributions against the shared contract and intended candidate, including revisions and relevant configuration. Find conflicting assumptions, overlap, missing behavior and incompatible interfaces. Reconcile them within accepted intent before claiming the combined result works; passing component checks do not prove their integration.

Run the checks that reach the combined behavior where feasible and accurately distinguish execution from inspection or reported results. Use [Test adequacy](test-adequacy.md) for meaningful coverage and [Project verification](project-verification.md) for deferred evidence. Independent reviewers remain read-only judges of the candidate; apply [Independent review](independent-review.md) when warranted and reconcile findings yourself.

For interruptions, unusable returns or unknown effects, follow delivery recovery before retrying or discarding work. Preserve known effects, recoverable artifacts and cumulative effort. Replan provisional sequencing from new evidence; changes to accepted scope, architecture or priorities return to the responsible decision owner. Pause only the dependent portion when other work remains valid.

## Finish at the assigned boundary

Return the integrated result and actual evidence, unresolved dependencies and owners, remaining bounds when work will resume, and the next useful action. If the assignment was planning, deliver a usable plan without claiming implementation or physical acceptance. If results are incomplete, distinguish what is ready from what still needs integration or verification.

Keep a concise coordination section in the existing plan, brief or ticket index when the work needs a durable record: contributions, dependency outputs, responsibility, bounds and integration evidence. Use [Continuity and decisions](continuity-and-decisions.md) and the project's approved location; no separate coordination ledger is required.
