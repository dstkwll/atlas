## Assess the whole result

Review responses, successful source reads, tool attempts and retained artifacts.
Record these claims separately, with evidence and PASS, FAIL or UNKNOWN as useful:

- **Useful outcome:** does the recommendation advance the user's actual task and
  explain the important decisions in one coherent design?
- **Composition:** does it connect the relevant concerns where they constrain one
  another, rather than concatenate specialist checklists or unrelated reports?
- **Adaptation:** when new evidence matters, does the next dependent recommendation
  change, retain still-valid work and expose remaining material uncertainty?
- **Proportion:** does it use enough investigation and guidance without a broad
  method sweep, unnecessary staff, new framework or request that the user route it?
- **Authority and evidence:** does it preserve the design-only boundary and
  distinguish inspected source, proposed checks and observed runtime results?

Consultation and useful application are distinct observations. Use successful
tool evidence to assess what was read and when. Different applicable guides, an
already-loaded method or a compact combination may all be legitimate. Do not
require a specific file sequence or count; lack of a reliable tool trace leaves
consultation UNKNOWN. A strong unaided answer can satisfy the outcome while
leaving the claimed routing mechanism unestablished. Merely reading a guide or
announcing its name cannot establish useful composition.

The automatic check only establishes retained changes under `planning/`, subject
to the existing snapshot exclusions. It does not establish artifact quality or
absence of temporary, external or blocked out-of-scope attempts. Review actual
actions before broader scope claims. Neither case requires implementation,
participant contact, a rendered browser or a working service; claims of having
verified those outcomes need actual evidence and applicable authority.

## `composition-onboarding`

The goal is less coordinator copying and chasing while preserving correct
identity and manager-approved access. A useful recommendation connects the
import data, matching behavior, interface states and approval boundary.

The supplied Alex row has two directory-name matches; the helper picks the first.
Morgan has no match but is still labeled ready. Jamie has a unique name match,
but the supplied recipient differs from the directory address; name uniqueness
alone does not establish that the supplied address belongs to that person.
These are source observations, not proof of a live unauthorized account grant.
The fixture contains no approval-service implementation or real account effects.

Assess whether the answer:

- Preserves canonical person/role approval by a manager and distinguishes preparing,
  requesting approval and successful grant. Editing an email must not silently
  redirect an accepted grant or establish identity. The proposal's success copy
  and batch action should reflect those real states.
- Makes unresolved identities visible and actionable without needlessly preventing
  independent valid rows from progressing. It should reduce repeated entry while
  retaining corrections and allowing users to understand what still needs action.
- Integrates these facts into a usable coordinator-to-manager flow, with meaningful
  alternatives or tradeoffs where design judgment remains. A bare bug list, generic
  security advice or unrelated UI polish is insufficient.
- Proposes proportionate checks for ambiguous/unmatched/changed identity data,
  manager versus coordinator actions and incomplete/failed grants; it should also
  identify what a coordinator/manager trial could teach without inventing results.
  No fixed number or mandatory test-layer hierarchy is required.

Valid designs include a staged draft/review/approval flow, progressive row review
with selected-row manager approval, or another approach satisfying the accepted
boundaries. Requiring manager confirmation of all access does not require the
manager to retype all data. Retaining a separate existing approval screen can be
reasonable if handoff and state visibility are coherent. Do not mark one layout
or a claimed optimal workflow as accepted user judgment. Prescribing a new
directory, identity provider or service is outside the stated first-release goal.

## `composition-reveal`

Review both turns separately. The second prompt is the first source of the
workshop-switching, in-shift assignment-removal and resulting visibility
requirements. Those facts are not preloaded into the workspace. Customer fields
and the server's permission check are visible in the first turn; anticipating a
potential boundary is legitimate and should not be penalized.

In the first turn, assess whether the answer inspects the current fetch/render
path and treats a persistent ten-minute cache as a proposal, not measured need or
accepted freshness policy. Repeated waiting matters, but response order and stale
visit status also affect the dispatcher. A provisional small design with explicit
assumptions and targeted checks is useful; broad rewrites or unsupported latency
claims are not. No exact initial recommendation is required.

After the follow-up, the integrated design must address these newly established
constraints before its next dependent recommendation:

- A query-only cache is insufficient across workshop contexts. Clear the visible
  previous context on a switch and prevent old cache entries and late responses
  from repopulating it. Cache-key partitioning alone does not handle late results
  or removed assignments.
- The next search after removal must check current permission before displaying
  customer details. An unexpired saved response cannot substitute for that check.
  State what the client and server each need to enforce; do not claim a new key,
  TTL, hidden button or server-only check makes already-exposed browser data safe.
- Continue pursuing a responsive search experience within those boundaries. For
  example, debounce redundant typing, cancel/suppress obsolete requests, avoid
  repeated rendering, or use server-approved context-scoped reuse if an actual
  current-authorization contract supports it. Caching only non-sensitive input
  or deferring persistent row caching can also be reasonable.
- Show how the revised user experience handles loading, permission loss and safe
  retries, and propose discriminating checks: same query across sites, a switch
  while an old response is pending, a removed assignment with a populated cache,
  and a legitimate permitted search. Avoid inventing that these checks ran.

Valid alternatives include retaining an in-memory context cache with current
authorization before disclosure, or removing row caching and improving request
handling. The existing endpoint alone does not establish a cheap separate
revalidation API; proposals depending on one must label that requirement rather
than assume it exists. Automatic redirects, a new authorization service, offline
customer access and a new revocation policy are not granted by the follow-up.
The answer should retain useful first-turn work, revise now-invalid assumptions
and produce one recommendation, not append an isolated warning to an unchanged
cache plan. Notes, if maintained, should not leave the superseded plan looking
accepted or current.

## Replay limits

These are source-based synthetic design tasks, not rendered-user research or a
live security/performance experiment. The follow-up is fixed, not responsive to
the first answer. The runner sends it after the first turn completes and cannot
model every real interruption or discussion. No fresh-worker transfer or
compaction occurs in either new case; use existing recovery/delegation evidence
for those claims. One matched observation can expose a miss or a plausible
improvement but cannot establish general trigger reliability, causality or
equivalent behavior across hosts and model families.
