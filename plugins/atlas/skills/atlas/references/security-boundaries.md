# Security boundaries

Use for a requested security review or work that changes or leaves uncertainty about authentication, authorization, credential or personal-data lifecycles, or model/tool authority. Untrusted input and external reachability warrant this method when they can affect a security property or reach a sensitive operation. Prospective account, permission, retention or integration design can qualify before a defect exists; a mechanical edit that leaves these boundaries unchanged needs no security review by default. Establish the assets, caller identities, trust boundaries, deployment assumptions and authorized inspection scope. Use approved local tools and current authoritative references where needed; no scanner installation is required by this runbook.

Trace an input to the sensitive operation. Identify validation and encoding at the relevant boundary, not merely the presence of a sanitizer somewhere. Parameterized database access, structured process arguments, path containment and context-appropriate output encoding address different problems. Framework defaults count only when the actual version and call path use them.

Separate authentication from authorization. Check object ownership, tenant isolation, privilege changes and background/admin paths. A route guard may identify a user without authorizing the selected record. Browser-origin policy is not access control. Test both allowed and denied cases, including access through alternate identifiers or stale credentials, in a permitted test environment.

For identity changes, trace account linking/unlinking, recovery, offboarding and privilege changes through existing sessions, tokens, caches and downstream consumers. Check when a removed entitlement actually stops working and whether a recovery or alternate sign-in path weakens the intended boundary. Derive expiry and revocation expectations from the accepted contract; do not impose universal lifetimes. A denied new login does not prove an old session or background integration lost access.

For model-connected operations, trace untrusted documents/messages through context assembly, model output and tool arguments to the sensitive effect. Verify caller, object and tenant authorization at the effect, independent of the model's proposed action. Role labels, schema-valid JSON or a second model do not make instructions trustworthy. Consider data disclosure as well as mutation; a model without tools may still expose protected context. Use synthetic bounded examples within authorized inspection scope.

For outbound requests and file handling, inspect redirects, resolved destinations, path normalization, archive extraction and resource limits where attacker control reaches them. For callbacks/webhooks, determine how authenticity, freshness and replay are enforced. For concurrent state changes, verify that checking permission or balance and applying the effect cannot race.

Follow secrets and private data through configuration, logs, errors, caches, exports and artifacts. Show redacted locations and exposure paths rather than reproducing sensitive values. An example credential may be harmless; an actual leaked credential is not fixed solely by moving it into an environment variable. Report the exposure and required owner action; rotation, deletion, incident notification or production changes need applicable authority.

For personal-data collection, export, retention or deletion, identify purpose, owner, allowed access and lifecycle of each relevant copy, including derived data, logs, caches, external processors and backups. Follow partial deletion and restored data to the promised outcome; consult [Data and migrations](data-and-migrations.md) for recovery interactions. Do not infer a legal retention period or broaden data collection from a generic checklist.

When credentials must change, identify consumers, ownership, replacement/revocation sequence, verification and residual exposure. Check that authorized consumers still work and that retired credentials fail at the relevant boundaries. Preserve redacted incident evidence; rewriting history or deleting logs is not a default remediation and may lose evidence. An owner action still needs the applicable authority described above.

Validate dependency findings against the resolved version, affected functionality and exposure. Do not treat every available update as required, or a clean scanner as proof of safety. When official advisories or deployment evidence cannot be reached, say which conclusion is limited.

Return concrete attack preconditions, reachable effect, missing/ineffective guard and evidence, plus bounded remediation and unverified paths. Accept zero findings when supported. Keep secure defaults and least privilege tied to actual boundaries instead of adding unrelated controls.
