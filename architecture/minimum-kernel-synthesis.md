# Minimum-kernel synthesis

**Status:** `EXPLORATION` — non-authoritative.

**Date opened:** 2026-09-01.

**Repository baseline:** `17172644e586e6987c308ed1d8b37edbcf481330`.

This document synthesizes the three cases required by [`minimum-kernel-exploration.md`](minimum-kernel-exploration.md). It does not amend numbered architecture, revoke an accepted decision, authorize implementation or deletion, or make the proposed kernel canonical.

## Decision state at a glance

**Provisional direction:** retain a small authority-and-proof kernel; collapse or delete presentation protocols and specialized workflow representations that no authority or executor consumes.

**Not ready for promotion:** the execution owner is not implemented, the ordinary case did not run through Atlas's real `trivial` path, and the contradiction case lacks its original exact receipt. Current numbered architecture remains authoritative.

## What the three cases establish

### 1. Upstream contradiction

A safe stop required exact accepted-design identity, exact frozen code, independent contradiction judgment, an atomic `BLOCKED`/`STALE` transition, immutable stale provenance, user-authorized forward correction, and fresh acceptance.

The case did not earn an automatic four-attempt repair episode, repeated predecessor copies, revision arithmetic, or automatic Program Design resumption.

### 2. Execution-proof compilation

A runnable task description was not enough. The graph was accepted only after it bound real runtime validators, exact input and validator identity, old/candidate provenance, fixture overlays, durable evidence, positive and negative behavior markers, and retained proof debt.

Later implementation evidence showed that the first two accepted literal validator commands failed in harness plumbing and required correction. The case therefore earned machine-readable executable truth plus pre-acceptance validator smoke testing. It did not earn Markdown grammar, duplicated body/frontmatter, self-attested readiness, exact H2 selection, or an exact seven-row review explanation as controller protocol.

### 3. Ordinary planning

A localized single-repository authority fix was safely completed by a tiny code deletion, one separating witness covering the real triggers, preservation checks, independent review, and human merge. It needed no new planning artifact or workflow state.

The case demonstrates the desired proportional outcome, but it did not exercise Atlas's implemented `trivial` route. A real low-complexity Gazetteer run remains necessary before promotion.

## Proposed minimum kernel

### A. One current authority receipt per accepted boundary

The receipt needs only facts used to decide whether accepted truth is current and consumable:

- artifact identity, version, and content hash;
- configured acceptance authority;
- exact independent review reference/hash when review is required;
- exact accepted upstream source and repository-baseline bindings;
- current, stale, or blocked state; and
- one legal atomic transition outcome.

Old accepted bytes and receipts remain immutable provenance. Presentation artifacts do not participate in current authority.

### B. Independent semantic judgment bound to exact bytes

Models and humans judge design quality, completeness, feasibility, contradiction, verticality, and proof sufficiency. Deterministic code verifies that the verdict is from the required judgment boundary and binds the exact candidate and sources.

The kernel needs a small routable outcome such as `PASS`, `BLOCKED`, or a separately confirmed upstream contradiction. Reviewer explanation may remain prose. Exact dimension names, ordering, and evidence-field grammar are not kernel requirements unless a real downstream decision consumes them separately.

### C. One machine-readable execution contract only when execution needs it

At the execution boundary, structured facts include:

- work identity and target repository;
- prerequisite graph and deterministic ready-work order;
- exact source and baseline bindings;
- exact commands or content-addressed executable assets;
- pre-acceptance smoke-test receipts proving each validator reaches an expected assertion or control result in its intended host;
- observable external prerequisites;
- exact input/candidate/fixture identities where proof depends on them;
- durable evidence destinations and minimum output identity/schema;
- sufficient deterministic behavior-to-proof bindings, with semantic, design, or quality review only supplemental; and
- explicit proof debt plus the authority allowed to retire it.

The contract may be one manifest or a small bound set of artifacts. Its physical representation remains open. Human explanation should not be mirrored merely to make a parser reread it.

### D. Exact candidate-tree and proof binding during execution

The future execution owner must bind validators, review, evidence, and accepted commit to the same candidate bytes/tree; reject drift; reconstruct one legal next action after interruption; and harvest required evidence before cleanup.

This remains part of the proposed kernel because proof of different bytes cannot authorize commit or acceptance. It is not yet empirically demonstrated by an Atlas execution owner.

## Reduction ledger

### Retain behavior

- immutable accepted artifact identity and provenance;
- configured authority distinct from producer claims;
- exact source and frozen repository bindings;
- independent semantic judgment;
- atomic legal state changes and visible blocking;
- executor-readable dependencies, inputs, commands, outputs, and proof bindings where execution consumes them;
- exact candidate-tree/evidence identity and behavior-level proof;
- validator-entry-point viability before `READY_FOR_EXECUTION`.

### Collapse or delete unless a consumer is demonstrated

- exact Markdown headings, section order, tables, markers, and rendered-line grammar;
- candidate `status`, `gate_ready`, dates, or similar producer attestations duplicated from authority state;
- HTML projection currency after canonical acceptance;
- prose mirrored between Markdown body, frontmatter, JSON index, review envelope, and control state;
- exact-H2 worker context declarations and duplicated purpose strings;
- fixed review-dimension schemas whose rows do not independently change controller action;
- D-082's automatic repair attempt budget, reservation protocol, repeated predecessor copies, revision arithmetic, and automatic resumption;
- separate special-case representation solely to preserve historical format versions;
- tests that defend those presentation protocols rather than authority, execution, or proof behavior.

### Still unresolved

- whether workers should receive complete accepted documents or selected excerpts;
- whether execution truth should be one manifest or a bound set of ticket and asset files;
- whether separate Stage 0–2 and Stage 3–5 controllers protect a necessary authority boundary;
- which tracer or enabling classifications a real scheduler consumes;
- how a smaller mechanism invalidates partially completed downstream work after an upstream change;
- the exact minimum restart record for a future executor.

## Promotion gate

Do not turn this synthesis directly into implementation. The next earned step is one bounded empirical run through the actual `trivial` path, using a genuinely low-complexity single-repository change. Measure:

1. what the user must decide;
2. which artifacts and confirmations Atlas creates;
3. which machine fields any later executor would actually consume;
4. whether the path stays one-unit and proportional; and
5. where current presentation grammar adds ceremony without safety.

If that run supports this synthesis, propose one reviewed canonical `CHANGE` that names exact retained invariants and deletion slices. Implementation should then proceed in reversible PRs that delete more mechanism than they add and retain separating witnesses for each real safety property.

## Evidence limitations

- The upstream contradiction's superseded exact acceptance and contradiction receipt were intentionally removed; its original chronology is credible but not fully reconstructible.
- Rejected execution-proof candidate bytes do not survive; their failures are reported by the retrospective, while the final acceptance is independently verifiable.
- The final accepted graph, review, ticket, and source hashes still match, but the frozen private repository trees could not be reverified because this machine lacks their local bindings.
- Later implementation evidence proves that at least two accepted literal validator commands were not executable as written. The recorded `READY_FOR_EXECUTION` state is exact but semantically overclaimed.
- No current first-party Atlas executor has consumed the accepted contract.
- The ordinary case is a real merged change outside Atlas's Stage 0–5 pipeline; the implemented `trivial` path remains test-backed rather than user-run-backed.

These limitations block canonical promotion. They do not erase the common result: authority, provenance, executable truth, and behavior proof earned their place; presentation grammar, duplicated representations, and specialized repair machinery have not.
