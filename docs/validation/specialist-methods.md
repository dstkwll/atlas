# Specialist methods: routing and application observations

The change adds product-interface review, user research/feedback synthesis,
quantitative visualization and conditional model post-training methods. Existing
security/data lifecycle, recovery, localization/CLI, cost, retrieval and verification
methods gain focused checks. Routes appear in the lead, specialist index and
relevant guides. The existing charter and portable-lead decision already support
selective methods; product direction is unchanged. No runtime, prescribed staff,
tool dependency or universal stage is added. Package 0.9.0 reflects capabilities.

## Intended selection boundaries

| Method | Intended trigger | Important neighboring boundary |
| --- | --- | --- |
| Product interface review | New/revised screen, hierarchy/workflow/clarity critique | Mechanical copy changes need no design menu; source is not rendered evidence |
| User research | Study planning, feedback synthesis, decisions dependent on actual users | Owner preferences and simulated personas are not participant evidence |
| Quantitative visualization | Quantitative encoding affects interpretation | Arithmetic lookup and nonquantitative diagrams need no chart audit |
| Model post-training | Fine-tuning, training signal or checkpoint integrity | Inference/retrieval changes need no training investigation by default |
| Security | Changed/uncertain identity, permissions, credentials, private-data lifecycle, model/tool authority or sensitive input boundary | Public endpoint wording alone does not warrant review |
| Data and migrations | Persistence, deletion/retention, backup/restore and recovery claims | Reading recorded backup status is not readiness assessment |
| User journeys | Interaction, accessibility, localization, CLI/script users | Source findings are separate from unavailable device execution |
| Performance | Slowness, resource growth or unit-cost regression | More total spend can reflect more useful work |
| Model/retrieval quality | Candidate generation versus ranking failures | Ranking cannot recover an upstream-excluded item |
| Project verification | Repeatable checks and incomplete/retried/sharded evidence | A green summary does not prove missing coverage |

## Evaluation design and structural checks

The [22 scenarios](../../evals/cases.json) use natural requests and synthetic raw
artifacts. [Semantic expectations](../../evals/specialist-review.md) remain outside
executing workspaces. Consultation, useful application, selectivity and authority
are separate judgments. Nineteen scenarios were prepared independently of the
implementation wording. Two Security diagnostics follow a source-review finding
and are not held out. One fresh archive-interface variant was prepared independently
after an earlier UI failure, without reading the amended method; its author knew the
broad failure, so it is not fully blinded or held out. The original 21 cases remain
unchanged. There are four negative controls and an interface-to-feedback
transition. Transition files exist initially and follow-ups are fixed, so this is
not an unpredictable human conversation.

All 39 evaluator correctness tests passed after adding the fresh variant, as did
skill validation, 207 package-local links and diff checks. No prose-matching grader
or runtime was added. These checks establish structure and evaluator sensitivity,
not agent judgment.

Independent source review found a Security entry condition broader than its
routing rows and then a missing explicit permission cue. Both were corrected;
fresh source inspection verified the selective condition and mechanical-edit
exclusion. The final fixed-text/download diagnostic pair subsequently exhibited
the intended selective behavior in one sample each.

blocked/interrupted attempts.** Eight completed samples used main; 26 used candidate
revisions. Across those revisions, all 22 new scenarios have a completed candidate
sample, alongside two retained-behavior cases and two repeated UI/control samples.
Host completion is not a behavioral pass. An independent assessor inspected reads,
responses, artifacts and captured actions. All attempts reported stopped hosts and
removed temporary authentication homes.

The main/candidate subset used matching requests, fixtures, host, model and effort
with explicit project-local Atlas activation, Codex app-server 0.153.4 and
`gpt-5.6-sol` at low effort, with a 180-second bound per trial. Per-attempt source
identities remain in local evidence. The 18 resumed samples used the final package
sources; earlier results are not reassigned to later instruction edits. The runner
uses case-list order, so the repeated UI batch ran original critique, copy control,
then fresh archive critique.

## Retained misses and interpretation

The interface guide requires final source/rendered/exercised coverage and disclosure
of unavailable announced checks. Source review found the amendment coherent, but
the original-case retest still omitted that disclosure. The fresh archive variant
did disclose it and made credible alternatives visible. This is **mixed application
evidence, not a verified general fix**. The original case is now a development case;
neither its rerun nor the fresh diagnostic establishes improvement causally.

Other narrow misses remain visible:

- Identity review claimed no files changed after importing Python created bytecode.
  Search diagnosis also created bytecode, without that blanket claim. No source or
  account change occurred. Snapshots omit `.git` and `__pycache__`, so
  `workspace_unchanged` cannot establish literal absence of file effects. The rubric
  now names that limit; captured actions and retained incidental artifacts were
  independently inspected.
- Chart review called the bars color-only despite their direct labels and different
  heights. The numerical reasoning remains useful; that extra criticism is unsupported.
- Cost review treated successful-job counts as evidence of preserved correctness.
  Output correctness was a goal, not supplied verification. Performance already
  requires quality/correctness checks, so this is incorrect application rather than
  demonstrated need for another instruction.
- Localization review promoted a member-selected locale into a requirement, while the
  brief leaves the locale source unspecified. That is a proposed policy, alongside
  the supported plural, direction, truncation and date findings.

Earlier minor counting and evidence-overstatement findings in candidate and baseline
returns remain in the retained assessment. Baseline research, feedback, deletion,
chart, transition and training diagnoses were already materially useful. These
single matched samples do not show that the added guides were necessary or superior.

## Interrupted attempts and limits

Six attempts were interrupted by storage errors during evidence capture. Three
more failed during host startup; one explicitly reported inability to initialize
SQLite state, but the cause of every startup error is unknown. All 15 remaining
prepared cases and three UI follow-ups completed with retained traces after
recovery; the original attempts remain counted alongside their replacements.

These synthetic tasks do not establish rendered UI behavior, actual participant
research, database restore, live account administration, training or production
readiness. Explicit activation does not test implicit host discovery. Single
samples and reviewer agreement do not establish reliability across models, hosts
or real conversations. The preselected bounded evaluation is complete, with the
misses above. It supports review of the selective-method integration, not a claim
that all relevant runbooks always fire or that visible design comparison is reliable.
Broader [trigger/design acceptance](https://github.com/dstkwll/atlas/issues/33)
remains open. No merge, release or installed-copy update follows from these observations.
