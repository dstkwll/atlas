# Atlas ideas from the Satchel work

These were the original proposals from the standalone-skills work. The owner subsequently authorized their assessment in [issue #52](https://github.com/dstkwll/atlas/issues/52), delivered separately in [draft PR #53](https://github.com/dstkwll/atlas/pull/53). That follow-up records their dispositions and bounded Atlas changes; this table preserves the initial rationale, not current task status. [Issue #50](https://github.com/dstkwll/atlas/issues/50) owns the Satchel delivery, which leaves `plugins/atlas/`, the Atlas marketplace entry and Atlas's behavior unchanged.

| Idea | Current evidence and possible benefit | Cost / evidence needed before changing Atlas |
| --- | --- | --- |
| Reconcile the two agent-writing methods | Atlas already has an internal adaptation of Matt's writing guidance; Satchel exposes a standalone adaptation from the pinned current source. Compare their useful distinctions and decide whether to share an authored source later. | Independent installability must survive. Sharing can introduce packaging/synchronization work; keeping separate adaptations can cause drift. A real consumer and explicit ownership decision should precede extraction. |
| Evaluate the three-reading check | Satchel explicitly checks literal obligations, implied/negative meaning and isolated-context interpretation. Atlas already protects exceptions and nearby scope, so this may be clarification rather than a missing capability. | Test a plausible misreading that current Atlas guidance fails to catch; avoid adding a ritual to every edit. |
| Check loaded-word compression against preserved obligations | The Satchel adaptation makes `tight` and `red` recognition tests explicit and warns against importing role, authority or intensity. This could help review terms such as tracer bullet, fog and legwork. | Atlas already defines several of these terms. Inventory only the affected terms and retain a no-change result if the meanings are already clear. |
| Recheck co-installed selection | Atlas routes authoring internally; Satchel has a directly discoverable writing skill. Explanation requests may also encounter Satchel's repair/teaching methods and Atlas's visual explanation. Neither package requires the other. | Observe actual host selection and instruction use before changing routing. Names alone are not a collision; do not add a controller to solve a hypothetical problem. |
| Refresh old local-marketplace observations | Isolated Copilot CLI 1.0.91 fixture checks registered a local multi-plugin marketplace and discovered its skills. Earlier Atlas validation documented a local-marketplace limitation. | Reproduce against the final package and distinguish local live registration from Git-backed transfer. Update dated validation evidence only through a separately scoped Atlas change. |
| Consider a general standalone handoff | A non-engineering user may need a portable continuation brief without activating the Atlas lead. This is the same deferred [context-handoff candidate](adaptations.md#other-candidates-considered). | Establish a representative research/admin continuation case and compare existing `atlas-handoff` before adding or extracting a skill. |

The proposals alone establish neither measured improvement nor authority to change Atlas. Neither plugin requires installing the other.
